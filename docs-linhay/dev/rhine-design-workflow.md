# Rhine Design 接入、设计评审与持续共建

本流程执行根 [AGENTS](../../AGENTS.md) 的长期规则；产品边界与迁移目录见 [DESIGN_SYSTEM](../../DESIGN_SYSTEM.md)，页面目录与运行入口见 [design](../../design/README.md)。适用于 Web 与独立原生设计任务，不扩大 CLI/HTTP、Wails 或原生产品维护范围。

## 先核对，再固定制品

1. 核对仓库/worktree、分支、未提交改动、技术栈、依赖与既有设计体系，保留已有工作；独立仓库的目录存在不产生维护授权。
2. 从实际消费版本读取 README、设计规范、交互模式、组件索引、相关契约及随包 skill；另查上游当前偏好、决策和匹配 open/closed issues。分别记录“当前包可用 API”和“尚未发布的设计决定”，不从展台、源码或关闭 issue 推断包可用。
3. 使用兼容的精确版本，或有固定来源、摘要与恢复步骤的制品；同步 manifest、lockfile、制品说明和随包 skill 入口，比较升级前后锁文件，解释必要的传递依赖变化。禁止浮动 main、修改 node_modules、复制组件源码或私有 CSS。
4. 优先公开组件、tokens、主题、布局和动效；产品只负责页面组合。Web 包 `@linhey/rhine-design` 与 GitHub `linhay/rhine-design` 拼写不同；iOS 来源 `linhay/rhine-design-ios` 的规范、版本与 UIKit 原生验收独立，其他技术栈先记录可复用规范和实现缺口。

## 设计稿先行

先在 space 写清 BDD、角色、状态、交互、验收和非目标，盘点有辨识度的视觉与动效并说明保留意图或改变理由。根 `design/` 保持页面目录，产品设计入口关联对应 space；同一期一个入口容纳多个场景。

实际包支持时优先官方 review 壳与协议。0.11.3 已导出 `@linhey/rhine-design/review`、`/review/vite`，官方构建生成的 index/canvas 属于同一评审入口实现，不手写第二套壳或复制通用工具栏。产品仅维护自己的目录、场景、维度、合成数据和验收记录。

本项目配置入口为 `Web/design/vite.config.ts`，命令为 `npm --prefix Web run design:dev`、`design:build`、`design:preview`；开发/预览继续固定 `127.0.0.1:34127` / `127.0.0.1:34128` 且 strictPort，与普通 Web 服务互斥，不抢占既有进程。准确 URL、构建目录与当前运行状态由 [design/README](../../design/README.md) 记录。

设计稿复用业务实际组件和样式，场景数据使用合成 DTO。评审配置独立于正式配置，不带生产 dotenv、代理、会话或真实接口；按官方契约安装 mock/平台适配与清理回调后再加载产品模块。未匹配请求不得回落真实服务；退出场景中止请求并清理监听器、计时器和动画。普通生产构建不得导入 review 模块、场景或设计入口，验证时检查实际构建输出。

新增页面、视觉重构和交互调整，先完成可交互设计验证，再接回业务。设计和实现同时授权时按顺序连续完成；只有设计授权时止于设计。纯后端或无界面变化的修复不强制增设设计阶段。Web 的只读 DTO、服务端检索/分页、权限、未知状态和操作结果保持原契约；不把设计迁移变为业务控制面。

## 持续反馈与临时适配

用户于 2026-10-30 明确授权：本项目任务内形成的规范、个人偏好、纠正、细节、成功组合、验证发现与组件缺口主动反馈到 [linhay/rhine-design issues](https://github.com/linhay/rhine-design/issues)，无需逐次确认，也不限于缺组件。

1. 先检索 open/closed issues 和相关规范，阅读匹配主题。已完整覆盖则记录关联；有新增信息则补充原 issue；独立可行动主题新建 issue。不要将具体设计问题堆入流程 issue。
2. 清楚标注用户偏好、产品约束、通用建议、已验证事实与待验证推断，保留适用范围；个人偏好不是所有项目的标准。
3. 写明匿名场景、设计意图、实际消费版本/固定制品、当前与期望行为、合成示例、验证证据和可观察验收条件。按需要建议规范、组合配方、组件、展台或回归验证，不默认增加 API。
4. 公开内容不得含内部文档、真实业务数据、内部地址、凭据、本机路径或设备标识；提交前审阅完整正文与附件。用结构化参数或 `--body-file` 保留多行文字，避免 shell 展开。
5. 提交后回读确认，将 issue/comment 链接写回 space、设计记录与交付说明。提交失败保留完整脱敏草稿、原因和待提交状态，继续独立工作；结果不确定先查回执，不能盲目重复发帖。

反馈授权不含公共源码改造、Git 提交推送、合并、正式发布或后台监控。规范未更新不阻止已授权产品工作：确认实际导出、契约、版本和已有组合均不能覆盖后，先查重反馈，再做最小可回退的局部适配。不得把适配扩成另一套组件库。

临时代码以 `Temporary design adaptation` 和 issue 链接标记；在 DESIGN_SYSTEM 的“临时方案／待规范复核”记录差异、文件、适用范围、制品版本、证据、复核触发与移除条件。工程标记不展示给产品用户。一般业务布局组合不是库缺口，无需为正常组合制造临时适配。

## 上游更新后的回接

后续同主题任务、收到更新信息或执行已授权的依赖升级时，主动核对关联 issue、规范、组件、展台和实际可消费制品，逐项区分：已反馈、已接受、已实现、已发布、本项目已验证。issue 关闭或源码合并不能跳过制品与消费端验证。

固定新制品后同步 manifest、lockfile、来源/摘要和随包 skill 记录，检查无关依赖漂移。用原验收场景验证产品组合行为等价，再移除已被覆盖的临时适配；保留未覆盖项的原因与明确移除条件。本流程随任务执行，不自行建立轮询或定时监控。

## 验证与交付

按实际 package scripts 运行匹配测试、类型检查、普通构建与独立评审构建。检查正式产物隔离，固定候选、工具版本、入口、日期与输出；共享服务启停和构建串行，按仓库治理执行适用总门禁。

Web 覆盖相关 400/520/880 宽度、200% 缩放、长文本、加载/空/错误、键盘、焦点、浮层和主题；记录 review CSS zoom 与浏览器原生 zoom 的区别。变化的动效必须实际观察播放、暂停、系统和手动减少动态、尺寸变化与卸载清理，静态截图不替代动态验收；未完整适配场景内所有动画，不声明 full/paused 评审控件。无新增动效时说明既有动效范围与不适用项目。

原生改动补真实运行入口证据，浏览器模拟不能替代 UIKit 或桌面验收。报告分别列通过、失败、跳过、未执行及原因，并区分设计稿、实际页面、主线整合、发布和用户验收阶段。最终说明实际消费版本/来源、接入范围、设计入口、验证结果、反馈链接与剩余缺口；自动沉淀优先修订本流程和原权威资料，再同步 space、索引与 memory。

消费验收补充：独立画布不包含真实宿主的悬浮面板工具条，接回产品后应测量标题/状态与工具条的几何交集，并让窗格动作复用页面标题行（SP-247），不为单个菜单额外保留空工具栏；不能靠覆盖库私有CSS修正。排除测试使用canonical/realpath临时目录，与构建模块图的真实路径一致。随包skill元数据可能落后于包版本，记录其原始摘要、不自行改写版本；实际导出决定API可用性。证据见[SP-245](../spaces/SP-245-rhine-design-adoption/plans/20261030-validation.md)。

整理提交补充：混合工作区按任务来源拆分共享文件的暂存内容；迁移后的组件若沿用尚未提交的前端helper，必须连同直接依赖和对应测试一起归档，不能留下无法构建的提交。设备/Node服务等独立工作继续留在工作区。对实际暂存树导出快照，先串行完成Git HEAD、依赖与工具准备，再运行测试与构建，不用含其他WIP的工作区绿色替代提交候选证据。
