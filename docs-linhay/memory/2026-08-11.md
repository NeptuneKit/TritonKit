## SP-166 / GitHub #203

- issue 事实：同一显式 runtime target 与同一可见/可用 AX 文本节点下，`triton wait --text <label>` 超时、`triton act find "<label>" --all` 成功但空输出，而 `observe tree`/`observe current` 立即包含该节点。
- 根因：embedded runtime 的三个查询面各自实现文本匹配。wait 只 trim 候选文本但 query 原样精确比较；find 用原始 `==` 精确比较且不过滤 hidden；只有 observe 稳定暴露 trim 后的文本。查询侧与候选侧归一化、可见性规则均不一致。
- 裁决：新增 TritonKitShared 共享归一化 `TKTextMatching.swift`（trim + `folding([.caseInsensitive, .diacriticInsensitive])` + substring/exact 两种模式），与 Android / iOS host wait 既有折叠一致；`TKWaitFindTextMatch` 与 `TKUIAssertEvaluate` 改走共享匹配；`act find`（`selectAXNodesByQuery`/`tapTargetCandidates`）改走共享匹配并排除 hidden 节点（与 wait 的 hidden 规则一致，observe 仍权威列出 hidden 节点）；deterministic test-run `match=exact` 显式传 `.exact` 保持原语义。
- `act find` 无匹配契约：`resolveTapTarget` 在零候选时抛出 `TKTapTargetResolutionFailure`，`cliErrorDetail` 映射 `text_not_found` 并 `ExitCode.failure`（非零退出），从结构上禁止“exit 0 + 空 stdout”；新增 contract test 固化该行为（该测试先行通过，作为回归 pin）。
